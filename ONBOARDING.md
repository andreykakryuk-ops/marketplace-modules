# Настройка и повседневная работа

## 1. Создайте владельца и сотрудников

После локального запуска откройте `/setup`: задайте свою почту и пароль. Повторная первоначальная регистрация отключается, когда создан аккаунт. В «Сотрудники» владелец создаёт аккаунты и назначает доступ. Ручная правка количества закрыта по умолчанию; сотруднику можно открыть именно её. Порядок и скрытые складские строки сохраняются отдельно для каждого человека.

При интеграции в ваш сайт Cursor должен связать эти проверки с **вашей** авторизацией. Наличие меню само по себе не даёт права на серверные действия.

## 2. Заполните основной склад

Добавьте реально закупаемые компоненты: товар/устройство, ремешок, упаковку, зарядку и другие позиции. Для каждой укажите название, фактическое количество и стоимость единицы. Названия исходных групп можно переименовать под ваш бизнес.

Стартовый остаток вводите один раз. Если позже пришла новая партия, используйте «Приход», а не повторно добавляйте её ручной правкой: иначе история и себестоимость будут неверны. Если средняя стоимость неизвестна, не выдавайте ноль за известную цену.

## 3. Создайте комплекты

В «Комплекты» создайте продаваемый артикул. В редакторе выберите компоненты и количество на **одну** единицу: например, 1 устройство + 1 ремешок + 1 коробка. Сохраните полный состав. Комплект без состава помечается как требующий настройки и не должен списываться как готовый к работе.

На основном складе находятся компоненты, в «Собрано на складе» — готовые комплекты. Не записывайте одну физическую единицу одновременно как свободный компонент и как готовый комплект.

## 4. Подключите свои API

### Wildberries

В кабинете своего продавца создайте актуальный API-токен с доступом **«Маркетплейс»** для FBS. Для опциональной загрузки FBW/FBO нужен также доступ **«Поставки»**. В настройках модуля введите ключ, нажмите «Проверить и сохранить WB»; FBW/FBO включайте только если используете их и у ключа есть разрешение.

Проверка обращается к списку новых FBS-заказов, а не меняет заказы. Сохранённый токен связан с продавцом; смена на другой кабинет отклоняется. Не включайте несколько работников синхронизации для одной базы.

### Ozon

В кабинете продавца найдите **Seller API Client ID** и ключ с разрешениями FBS, включая список и чтение отправления. Введите их в Ozon Seller API, пройдите проверку. Client ID рекламного Performance API сюда не подходит. Рекламный API для этих четырёх разделов не нужен.

После сохранения фоновые чтения идут примерно раз в 60 секунд, пока процесс приложения работает. Ошибки/лимиты API могут задержать цикл; отсутствие новых заказов не доказывает поломку. В настройках есть статус и ручное обновление.

## 5. Свяжите артикулы

По умолчанию артикул готового комплекта должен точно совпадать с `article` WB или `offer_id` Ozon. Различия в символах, пробелах и регистре не исправляются догадками.

Если артикулы отличаются, используйте форму **«Связь артикулов с комплектами»** в настройках:
- WB: введите **артикул продавца**, не числовой nmID карточки.
- Ozon: введите **числовой SKU Ozon**, не Seller Client ID и не артикул продавца.
- Выберите уже созданный комплект с заполненным составом и сохраните связь.

Несколько артикулов можно связать с одним физическим готовым товаром: его остаток не дублируется. Если товары отличаются составом, заведите разные комплекты. Неизвестные артикулы отображаются как несопоставленные; их нельзя молча списать с произвольной позиции. После настройки дождитесь следующего цикла или обновите поставки вручную.

## 6. Поставки и сборка

Схема: **заказ → соответствующий комплект → потребность компонентов → сборка → проведение → документ движения**.

- Новые FBS-заказы появляются автоматически как «Актуальная FBS поставка WB/Ozon». Переведённые в сборку/поставку заказы образуют соответствующие партии. Состояние меняется вслед за кабинетом продавца.
- Открытый FBS-заказ резервирует потребность, но физическое количество ещё не списывается. Сводка учитывает уже готовые единицы и нехватку компонентов. Резерв другой партии нельзя расходовать в обход проверки.
- Галочка «Собрано» — отметка работы, **не самостоятельное списание**. При новых заказах в партии ранее собранные единицы сохраняются, добавленные не считаются собранными автоматически.
- «В склад упакованных» собирает новую партию из компонентов в готовый склад. «Провести» выполняет локальную отгрузку: использует готовые остатки и, когда требуется, компоненты новых комплектов. Нехватка/неполный состав блокируют операцию.
- Повторная синхронизация уже проведённого заказа не должна снова уменьшать остаток: обработанные идентификаторы сохраняются вместе с документом.
- Отменённые заказы удаляются из открытого спроса; повторное распределение по партиям сохраняет отмеченную сборку по конкретным заказам.

Отправку, подтверждение заказов и этикетки в WB/Ozon выполняйте по правилам их кабинетов. Модуль не заявляет такую внешнюю запись. Существующие исторические отгрузки при первом подключении не нужно проводить повторно; случаи «уже в доставке, но не было локальной истории» требуют отдельной сверки.

## 7. Приход

Выберите основной компонент, количество новой партии и закупочную цену **за единицу**. Проведение увеличит количество и сохранит документ/автора. Средняя цена рассчитывается по оставшемуся старому остатку и новой партии: `(старое количество × старая средняя + приход × цена партии) / новое количество`, с округлением до 0,1 ₽ как в исходном проекте. Последняя закупочная цена хранится отдельно для сводок поставок.

## 8. Контрольный пример без реальных заказов

На отдельной тестовой установке:

| Шаг | Ожидаемый результат |
|---|---|
| Компоненты: 50 устройств по 500 ₽, 100 ремешков по 50 ₽, 100 коробок по 10 ₽ | Три самостоятельных остатка |
| Комплект TEST-KIT: по 1 каждой позиции | Себестоимость комплекта 560 ₽ |
| Складская сборка 10 TEST-KIT, отметить строки и провести сборку | Компоненты 40/90/90; готовых 10 |
| Ручная отгрузка 5 готовых TEST-KIT | Готовых 5; компоненты по-прежнему 40/90/90 |
| Приход 10 устройств по 700 ₽ | Устройств 50; средняя цена 540 ₽ |
| Повторная загрузка тестового FBS-снимка | Никакого повторного физического списания; этот сценарий также проверяет `npm test` |
| Попытка провести при нехватке / с пустым составом | Отказ без частичного изменения остатка |

Потом проверьте вход сотрудника, ограничения API/правки остатков и личную видимость строк. Лишь после этого переносите свой фактический остаток и подключайте рабочие кабинеты.
