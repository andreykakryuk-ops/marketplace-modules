## В существующий Next.js сайт

Перенесите страницы в свободный namespace, например `/warehouse`, `/warehouse/shipments`, `/warehouse/receipts`, `/warehouse/kits`, и согласуйте меню. В пакете ссылки и `fetch` начинаются от корня; при переносе нужно обновить **все** маршруты, `redirect`, `router.push`, `revalidatePath`, API статусов и версий. Не копируйте его root layout/proxy поверх layout/proxy хоста.

Подключите существующие user ID и роли через `lib/session.ts`/`lib/access.ts`. Сохраните проверку актуального права при каждом Server Action. Секретные серверные модули нельзя импортировать в клиентские компоненты, даже если endpoint скрыт из меню. Запускайте фоновый scheduler один раз и только в Node runtime, не при сборке.

## Другой стек или БД

Чистые расчёты `bom.ts`, `cost.ts`, `fbs-assembly.ts`, `procurement.cjs` и нормализацию можно перенести в service layer либо выполнить в отдельном Node сервисе. UI React адаптируется к API хоста. Определите endpoints чтения склада/поставок, прихода, комплекта, отметки сборки и проведения, исходя из функций `app/actions.ts`; типы полей задаёт `lib/types.ts`.

Файловая версия хранит JSON в `data/` и использует атомарную запись. Для БД перенесите **в одну транзакцию** физические изменения, документы, обработанные external IDs и маркер применённого снимка. Проверка нехватки и stale quantity должна проходить под тем же lock. Иначе два сотрудника/два worker могут списать одно и то же. Не заменяйте запись JSON набором независимых UPDATE.

Сущности: items, kits/kit_lines, shipments/lines, shipment_documents, receipts/lines, movements, users, access, personal row layouts, external handled IDs, FBS assembly per order unit, snapshot application markers. Сохраните привязку к кабинету; текущая самостоятельная версия — один WB и один Ozon, а не готовая система многоклиентской изоляции.

## Автоматическая синхронизация

Встроенный процесс читает WB новые/актуальные FBS заказы, статусы и существующие партии; Ozon читает `/v4/posting/fbs/list` и восстанавливает отслеживаемые отправления через `/v3/posting/fbs/get`. Публикация только после полной пагинации и проверки; внешних операций отгрузки в этих коннекторах нет. При переносе на serverless вынесите scheduler в cron/worker с общим lock и постоянной БД. `FBS_SYNC_ENABLED=0` останавливает общий scheduler для изолированных тестов/обслуживания.

Ключи вводятся обычной формой; WB продавец привязан через claims токена и подтверждённый API-доступ, Ozon — через Seller Client ID и роли. Не подделывать сессии хоста. При смене продавца нужна контролируемая миграция/отдельная установка; простая замена идентификатора нарушает идемпотентность.

## Опциональный адаптер прогноза закупок

В `lib/procurement-service.ts` намеренно отделён источник общей истории спроса: исходные аналитика/RNP/финансы не переносятся в четырёхраздельный пакет. Впишите ваш существующий источник либо атомарно сформируйте серверный `data/demand-input.json`:

```json
{
  "schemaVersion": 1,
  "obtainedAt": "<текущее ISO-время>",
  "complete": true,
  "sources": [{"name": "Мой магазин · WB", "period": "<start> — <end>", "ready": true}],
  "rows": [{"key": "wb:my-store:article", "source": "Мой магазин · WB", "finishedItemId": "<ID комплекта>", "daily": 5, "stock": 40}]
}
```

Числа в примере синтетические. `daily` — фактические заказы артикула за полный выбранный период / число дней, `stock` — подтверждённый доступный остаток соответствующего артикула на площадке. Учитывайте все подключённые магазины и исключайте дубли. Составы множат спрос на количество компонента; готовые локальные комплекты считаются один раз. Свежесть входа — 2 часа; неполный/неизвестный источник нельзя отмечать complete. Список новых FBS заказов не является полной 28-дневной историей продаж. API-ключей в этом JSON нет.

## Эксплуатация

- HTTPS, своё окружение и резервирование persistent `data/`. До открытия `/setup` в интернет создать владельца локально/в закрытом контуре.
- В архив/репозиторий входят исходники и пустой seed; не добавлять runtime `data`, `.env.local`, `.next`, node_modules, session-secret и auth.json.
- Проверьте CI после адаптации: `npm run check`, `npm run build`, затем контрольную цепочку и права на тестовых данных. Реальные подключения получателя требуют его собственных ключей и разрешений.
